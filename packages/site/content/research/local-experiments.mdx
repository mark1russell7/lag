We did nine experiments in this repository from 2026-10-07 to 2026-10-16. They measured facts that no document gives.

E1 measured the order of the event listeners at the target of an event. E2 measured the timers of an idle page in three engines. E3 measured the calibrated DriftLag on the same machine. E4 measured when the IndexedDB writes and the fetches of a worker complete while the main thread is blocked, also in Safari. E5 measured DriftLag during a sustained load.

E6 measured the other output APIs of a worker during a block. E7 measured what another page of the origin sees of a hang, also in Safari on iOS. E8 measured the cost of an async context on the main thread, and its effect on the values of the monitors. E9 measured the animation frames, the idle callbacks and the timers of a cross-origin frame off the screen.

The results changed the library in five ways. An explicit hook, not the order of the listeners, records the final values before each flush. DriftLag subtracts a calibrated baseline. The probes that use `setTimeout(0)` start in a message task. A probe of message tasks must show an idle thread before the baseline of DriftLag increases.

E4 and E6 found a limit of the hang reports and of the hang journal in WebKit and Safari. E7 found a way around it: the peer hang watch. E8 did not change the library. It gives the data for the default context manager of otel-ts and for an add-on of lag. E9 made the frame-timing monitor pause while its frame is off the screen.

## E1: the order of listeners at the target

**Question.** When two listeners are on the target of an event, does a capture listener start before a bubble listener that the page added earlier? The DOM standard says yes: at the target, the capture listeners start in the capture pass, and the other listeners start in the bubble pass.

**Method.** The experiment used Vitest browser mode with the Playwright provider. In each case, it added a bubble listener first and a capture listener second. Then it dispatched one event and recorded the listener that started first.

| Target | Chromium 145.0.7632.6 (headless) | Firefox 146 | WebKit (Safari 26.0) |
|---|---|---|---|
| `window`, custom `Event` | Bubble (the order of registration) | Capture | Capture |
| `window`, `PageTransitionEvent("pagehide")` | Bubble (the order of registration) | Capture | Capture |
| `document`, custom `Event` | Capture | Capture | Capture |
| `document`, `Event` with `bubbles: true` | Capture | Capture | Capture |
| Element (`document.body`) | Capture | Capture | Capture |

**Meaning.** The target of `visibilitychange`, `freeze` and `resume` is `document`. Thus the capture listeners of the monitors start before the listeners of an exporter in all three engines. The target of `pagehide` and `pageshow` is `window`. In Chromium, the listener that the page added first starts first there. Thus an exporter that added its `pagehide` listener before the monitors can flush before the monitors record their final values.

**Change in the library.** The fix does not depend on the order of the listeners. `AllMonitorHandles.flush()` records the values that the monitors keep until a checkpoint. At the start of each flush, otel-ts starts each `onBeforeFlush` listener. The setup connects the two: `otel.onBeforeFlush(() => monitors.flush())`.

Later, the state machine became the package `page-lifecycle-tracker`, with a tracker that the page shares. The otel-ts library flushes in its `export` phase, after the monitors recorded the transition.

Refer to [`setup-all-monitors.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag/src/setup-all-monitors.ts), [`LifecycleStateMachine.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag/src/LifecycleStateMachine.ts) and the [quick start](/docs/getting-started). The browser test [`lifecycle.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/lifecycle.test.ts) keeps a check of the `document` case.

## E2: the timers of an idle page

**Question.** How long does one step of a chained `setTimeout(5)` take on an idle page? Which lag does the old DriftLag report on an idle page? The old DriftLag chained 20 steps of 5 ms and reported the elapsed time minus 100 ms.

**Method.** The experiment used the headless engines of Playwright on Windows 11. It measured each value on an idle page.

| Measurement | Chromium 145 | Firefox 146 | WebKit (Safari 26.0 build) |
|---|---|---|---|
| Median step of `setTimeout(5)` | 5.7 ms | 16 ms | 15 ms |
| Shortest step | 5.0 ms | 9 ms | 13 ms |
| Old DriftLag, idle median lag | 15.8 ms | 211 ms | 211 ms |
| `setTimeout(0)` from a `setInterval` callback (8th repeat), median | 5 ms | 16 ms | 16 ms |
| `setTimeout(0)` from a message task, median | 0 ms | 0 ms | 15 ms |
| `requestIdleCallback` | Yes | Yes | No |
| `performance.interactionCount` | Yes | Yes | Yes |

**Meaning.**

- For a 5 ms timeout, Firefox and WebKit on Windows use the 15.6 ms timer tick of the system. Chromium asks for a 1 ms tick. This agrees with the timer rules in [clocks and timers](/research/clocks-and-timers).
- On an idle page, the old DriftLag reported more than 200 ms of lag for each 100 ms window in Firefox and WebKit, and 16 ms in Chromium. Thus the old probe measured the timer granularity, not the lag.
- A `setTimeout(0)` from a nested timer gets the 4 ms clamp in Chromium, and the system tick in Firefox and WebKit. From a message task, Chromium and Firefox start it at once.
- The WebKit build for Windows is not Safari on macOS. Safari on macOS aligns nested timers to a grid of 4 ms, and of 30 ms in Low Power Mode ([WebKit `DOMTimer.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/DOMTimer.cpp)).

**Change in the library.** MacrotaskLag and SchedulingFairness start each measurement in a message task ([`message-task.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag/src/message-task.ts)). A message task has the timer nesting level 0, thus the `setTimeout(0)` measures the queue and not the clamp. Without `MessageChannel`, MacrotaskLag starts the measurement in its `setInterval` callback and has a floor of approximately 4 ms.

## E3: the calibrated DriftLag

**Change.** DriftLag subtracts the idle duration of one step. The baseline is the mean of the recent steps that are not longer than the median plus max(4 ms, half of the median). The lag of a window is its duration minus the number of steps multiplied by the baseline ([`DriftLag.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag/src/DriftLag.ts)).

**Method.** The experiment used the same machine and engines as E2. It recorded approximately 30 idle windows, then blocked the main thread for 300 ms.

| Measurement | Chromium 145 | Firefox 146 | WebKit |
|---|---|---|---|
| Baseline step | 5.7 ms | 15.5 ms | 15.6 ms |
| Idle median lag (approximately 30 windows) | 0.1 ms | −0.3 ms | −0.4 ms |
| Idle p90 lag | 3.1 ms | 1.3 ms | 1.6 ms |
| Lag after a 300 ms block | 297.4 ms | 282.7 ms | 294.6 ms |

**Meaning.** The idle error went from 15.8 ms to 211 ms down to less than 0.5 ms. The resolution of the measurement is one step. A block can start immediately after a step, thus the lag of a block can be less than its duration by up to one step. That step is 16 ms in Firefox.

A first version used the median as the baseline. It gave an idle median lag of 3.3 ms in Chromium, because timer jitter is skewed to the right. Thus the baseline is a mean of the steps that are not blocks.

**Check in the repository.** The browser test [`drift-accuracy.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/drift-accuracy.test.ts) keeps a check of the two properties. The idle median must be less than 5 ms from 0, or 10 ms in a window without focus. On macOS, the timers of an app that is not in front can be late. After a 300 ms block, the largest lag must be more than 300 ms minus the baseline minus 10 ms, and less than 340 ms. Without focus, the margin is 20 ms, because some steps of Safari are late and its baseline is longer than its usual step.

**A later finding.** The granularity can change while a page is open. The CDP tests found such a change in Chromium on Windows. After the page was hidden and shown again, the steps took 15.6 ms instead of 5.5 ms. The baseline of the last 100 steps followed the change slowly, and DriftLag reported windows of 160 ms of lag on an idle page. Thus DriftLag accepts a row of 10 steps that agree with each other as a new granularity ([DriftLag](/docs/monitors/drift-lag)).

## E4: the input and output of workers during a main-thread block

**Question.** Can a worker write to IndexedDB and send a request while the main thread of its page is blocked? The hang report and the hang journal of the [worker monitor](/docs/monitors/worker-lag) depend on it.

**Method.** The probes are in [`worker-io.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/worker-io.ts). Each probe starts an operation in a worker, and then it blocks the main thread for 2 s. It records when the operation completes, as the time after the start of the block. The experiment used the Playwright builds on Windows 11, with these probes:

- A dedicated worker writes one record to IndexedDB.
- A dedicated worker sends a `fetch` with `keepalive`.
- A shared worker writes to IndexedDB and then sends a `fetch` each 100 ms, on its own timer. The probe counts the operations that complete during the block, with a margin of 100 ms at the start and at the end. The shared worker uses its own timer, because a message from the page can also wait.
- A service worker (`public/lag-sw-probe.js`) does the same as the shared worker, on its own timer of 100 ms (2026-10-08). A service worker operates outside the page, thus it could possibly keep the hang journal where a dedicated worker cannot.

A CI job operated the same probes in Safari 26.6.2 on a GitHub macOS runner, through safaridriver (2026-10-08). The Safari column comes from the log of that job. The log gives the count of the service worker. For the other probes, the log shows that the tests passed with the expectations of WebKit.

| Measurement | Chromium | Firefox | WebKit | Safari 26.6.2, macOS (CI log) |
|---|---|---|---|---|
| IndexedDB write of a dedicated worker, complete after | 7 ms | 36 ms (58 ms in a second run) | 2015 ms (2008 ms in a second run) | After the block |
| `fetch` with `keepalive` of a dedicated worker, complete after | 19 ms | 14 ms | 2013 ms | After the block |
| Operations of a shared worker that completed during the block, of all its completed operations | 18 of 28 | 16 of 26 | 0 of 26 | 0 |
| Operations of a service worker that completed during the block, of all its completed operations | 18 of 28 | 17 of 27 | 0 of 29 | 0 of 27 |

In WebKit, a message that the page posted to a shared worker immediately before the block also arrived only after the block, at 2003 ms.

**Meaning.** Chromium and Firefox complete the IndexedDB requests and the network requests of a worker during the block. WebKit completes them on the main thread of the page, after the block. This is also true for a shared worker and for a service worker. Safari 26.6.2 on macOS behaves the same as the WebKit build of Playwright for Windows.

In WebKit and Safari, the timer of the worker continues, thus the worker detects a hang. But it cannot send its hang report or write the hang journal until the main thread operates again. Thus there, a page that does not survive its hang leaves no record and no report. A service worker is no way out: its writes and fetches also wait for the main thread of the page.

**Change in the library.** The code does not change. The pages [worker lag](/docs/monitors/worker-lag) and [survivorship bias](/docs/concepts/survivorship) give the limit.

**Check in the repository.** The browser test [`worker-io.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/worker-io.test.ts) operates the four probes in Chromium, Firefox, WebKit and Chrome, and in the CI job in Safari. In WebKit and Safari, it expects that the write and the fetch complete after the block. It also expects that the shared worker and the service worker complete no operation during the block there.

In the other browsers, it expects the write and the fetch before the end of the block. A completion 25 ms or less before the end of the block counts as a wait, because the worker and the page read different clocks. On a busy CI runner, a write of Firefox completed after 1141 ms of a block of 2000 ms: slow, but not a wait. It also expects more than 5 operations of the shared worker and of the service worker there. Thus the test fails if an engine changes its behavior.

The browser test `hang-journal.test.ts` skips itself where a probe finds that the IndexedDB requests of a worker wait for the main thread. The probe uses a block of 500 ms. Thus the skip comes from a measurement, not from the name of the browser. In the CI log, the test skips itself in Safari.

## E5: DriftLag during a sustained load

**Question.** Does DriftLag report a sustained load of tasks of the same length? The baseline comes from the recent steps. Thus a load that makes all steps longer can look like a new timer granularity.

**Method.** The page calibrated DriftLag for 2 s. Then it kept the main thread busy for 4 s with a chain of equal tasks, and then it was idle for 1.5 s. The experiment used the Playwright builds on Windows 11 (2026-10-08).

There were two loads. In the first, each task of 20 ms starts the next task with a message. In the second, each task of 30 ms starts the next task with `setTimeout(0)`, thus 4 ms later. The table gives the lag as a part of the time of the windows.

| Load | Chromium 145 | Firefox 146 | WebKit |
|---|---|---|---|
| Message tasks of 20 ms | 85% for 2.5 s. Then the baseline increased to 39 ms, and the lag decreased to 6%. | 25% for 1 s. Steps of 20 ms are in the jitter limit of steps of 15.6 ms, thus the baseline increased to 20 ms. The lag was 0 after 2 s. | Approximately 0 after 0.5 s. A row of steps of 31 ms was a new granularity after 10 steps. |
| Timer tasks of 30 ms | Approximately 0 from the start. A row of steps of 34 ms was a new granularity. | 67% for 2 s. Then the median increased to 42 ms, and the lag decreased to 12%. | 66% for 2 s. Then the median increased to 41 ms, and the lag decreased to 14%. |

**Meaning.** The calibration of E3 hides a sustained load. The lag decreased to less than 15% in each case within 4 s, and to approximately 0 in three of the six cases. The steps of a busy thread agree with each other, or the median becomes a busy step. The [worker monitor](/docs/monitors/worker-lag) measures these loads correctly, because it does not use the timers of the page.

**Change in the library.** A probe of message tasks must show an idle thread before the baseline increases ([DriftLag](/docs/monitors/drift-lag)). On an idle thread, a message starts at once. On a busy thread, it waits for the current task. A check is an idle probe, 3 steps, and a second idle probe. The browser tests of the change found three behaviors of the engines:

- **A probe changes the timing.** A probe keeps the thread awake. In Chromium, a probed step took 0.7 ms less than an idle step, and 2.5 ms less one time. The next step took up to 3 ms more (11 ms instead of 8 ms). A first version used the probed step as the idle duration, and gave 48 ms of lag in each window of an idle page in Chrome. Thus the probed step and the next step are not recent steps.
- **Messages wait in WebKit for Windows.** A chain of messages posted 84 messages in 100 ms there, and more than 13,000 in Chromium and Firefox. After an idle period, the first message waited 12 ms to 17 ms: the next timer tick of the system. Thus the probe finds no idle step there, and DriftLag operates as before the change.
- **Irregular steps in Firefox.** For some seconds after a load, the steps changed between 8 ms and 16 ms. A first version lowered the confirmed value to the recent baseline of one window. Then each window had 6 ms to 10 ms of lag. Thus the confirmed value decreases only to the highest recent baseline of 3 windows.

**Result.** The browser test [`drift-load.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/drift-load.test.ts) uses a load of 3 s. The table gives the lag in the second half of the load. The rows of Windows 11 come from three runs of four browsers at the same time. The rows of GitHub runners come from the logs of one CI run:

| Browser | Platform | Message tasks of 20 ms | Timer tasks of 30 ms, 4 ms apart |
|---|---|---|---|
| Chromium 145 | Windows 11, three runs | 80% to 86% | 78% to 85% |
| Chrome 153 | Windows 11, three runs | 80% to 86% | 79% to 85% |
| Firefox 146 | Windows 11, three runs | 24% to 29% | 53% to 72% |
| WebKit (Playwright) | Windows 11 | The test skips itself | The test skips itself |
| Chromium 145 | Linux, GitHub runner | 87% | 85% |
| Firefox 146 | Linux, GitHub runner | 75% | 84% |
| WebKit (Playwright) | Linux, GitHub runner | 60% | 79% |
| Safari 26.6.2 | macOS, GitHub runner | 62% | 77% |

In WebKit on Linux and in Safari on macOS, a probe on an idle page measured 0 ms of busy time. Thus only the WebKit build for Windows makes a message wait.

After the load, the median lag of a window was between −9 ms and 8 ms, in windows of approximately 100 ms. In Firefox on Windows, an idle step already takes 15.6 ms. Thus a step that waits for a task of 20 ms gives only 4.4 ms of lag.

**Check in the repository.** `drift-load.test.ts` expects more than 10% lag in the second half of each load. After the load, it expects a median lag of less than the idle median lag before the load plus 10% of a window. A negative idle median counts as 0. It skips itself if a probe on an idle page posts fewer than 400 messages in 100 ms. The WebKit build for Windows posts 122 to 278 messages, and the other WebKit builds in CI post 580 to 920.

The check after the load does not use the windows in which the browser stopped its timers. In the iOS Simulator, it also skips itself when the timers of the browser were slower after the load (refer to [the limits of the tests](/docs/testing/strategy#limits)).

The unit tests of `DriftLag.load.test.ts` use a simulated thread with a timer queue and a message queue. They simulate the three behaviors above.

## E6: the other output APIs of a worker during a block

**Question.** E4 found that IndexedDB and `fetch` of a worker wait for the main thread in WebKit. Can a worker of a blocked page write or send through another API? Each one could keep the hang journal in WebKit and Safari.

**Method.** The probes are in [`worker-io.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/worker-io.ts). The worker first prepares the operation, for example it opens the file. Then the page posts a message that starts the operation, and it blocks its main thread for 2 s. The worker records when the operation completes.

For a WebSocket, a server in Node (`commands/probe-socket.ts`) records when the message arrives, with the wall clock of the machine. The page uses the same wall clock, through `performance.timeOrigin`.

Three operations use the origin private file system (OPFS). They are a write and a flush through a `FileSystemSyncAccessHandle`, a write through a `FileSystemWritableFileStream`, and a file lookup. The other operations are `Cache.put()`, an asynchronous and a synchronous `XMLHttpRequest`, and a WebSocket message. The Playwright builds operated on Windows 11, in two runs (2026-10-08). Safari 26.6.2 operated in the CI job on a GitHub macOS runner, in two runs.

| Operation of a dedicated worker, complete after | Chromium 145 and Chrome 153 | Firefox 146 | WebKit (Playwright, Windows) | Safari 26.6.2, macOS |
|---|---|---|---|---|
| IndexedDB write | 42 ms | 44 ms | 2005 ms to 2036 ms | 2023 ms |
| OPFS: sync access handle write and flush | 6 ms to 45 ms | 2 ms to 40 ms | No OPFS in this build | 2001 ms to 2002 ms |
| OPFS: writable stream write and close | 13 ms to 16 ms | 37 ms to 43 ms | No OPFS in this build | 2003 ms to 2008 ms |
| OPFS: `getDirectory()` and `getFileHandle()` | 2 ms to 3 ms | 8 ms to 14 ms | No OPFS in this build | 2000 ms to 2002 ms |
| `Cache.put()` | 29 ms to 98 ms | 28 ms to 75 ms | 2011 ms to 2023 ms | 2004 ms to 2009 ms |
| `XMLHttpRequest` | 30 ms to 103 ms | 2073 ms | 2014 ms | 2005 ms |
| Synchronous `XMLHttpRequest` | 16 ms to 315 ms | 2017 ms to 2065 ms | 2012 ms to 2176 ms | 2004 ms to 2058 ms |
| WebSocket message, at the server | 0 ms to 3 ms | 2000 ms to 2002 ms | 2016 ms to 2048 ms | 2001 ms |

**Meaning.** In WebKit and Safari, each output API of a worker waits for the main thread of the page. Thus no API of a worker can keep the hang journal there. In the source of WebKit, the worker side of each API posts its work to the main thread of the web process. Examples are `WorkerThreadableLoader`, `IDBConnectionProxy`, `WorkerFileSystemStorageConnection`, `CacheStorageConnection` and `WorkerThreadableWebSocketChannel`.

In Firefox, the storage APIs of a worker complete during the block, but an `XMLHttpRequest` and a WebSocket message wait. Thus Firefox operates them through the main thread. The hang report of the worker uses `fetch`, which completes during the block in Firefox (E4). Chromium completes all of them during the block.

**Change in the library.** The code of the journal does not change. The [peer hang watch](/docs/monitors/peer-hang-watch) uses another page of the origin instead of a worker (E7).

**Check in the repository.** [`worker-io.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/worker-io.test.ts) operates each probe in Chromium, Firefox, WebKit and Chrome, and in the CI job in Safari. It expects each operation after the block in WebKit and Safari. In Firefox, it expects an `XMLHttpRequest` and a WebSocket message after the block. It expects all others during the block. A test skips itself where the worker does not have the API.

## E7: what another page of the origin sees of a hang

**Question.** E6 found no output API that a worker can use during a hang in WebKit. Another page of the origin has its own main thread. Can it see the hang of a page, and the end of a page that closes during its hang?

**Method.** The test page watches a peer page ([`peer-tab.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/peer-tab.test.ts)). A command opens the peer page as a second top-level page: with Playwright, or as a new window with WebdriverIO in Safari. The peer page holds a Web Lock until it closes. Its main thread and a dedicated worker each send a heartbeat through a BroadcastChannel each 100 ms. It also sends a message in `pagehide`.

The peer page then blocks its main thread for 4 s, and the test page records the heartbeats and examines the lock.

At the start of the block, the peer page sends a message with the time. The measurements start at that time, because the answer to the command that starts the block can come late. In one run of Safari on a GitHub macOS runner, the answer came more than 1 s after the start of the block. In a second case, the peer page blocks for 20 s, and the test closes it after 2 s. The test page asks for the lock of the peer page, and it records when it gets the lock. The measurements use the times of events, not of timers, because the test page can be hidden.

The Playwright builds operated on Windows 11 in three runs, and on Linux in CI. Safari 26.6.2 operated on a GitHub macOS runner, also with a block of 90 s. Safari 26.5 operated in the iOS Simulator of the same runner, with Xcode 26.6.

| Measurement | Chromium 145 and Chrome 153 | Firefox 146 | WebKit (Playwright) | Safari 26.6.2, macOS | Safari 26.5, iOS Simulator |
|---|---|---|---|---|---|
| The test page operates during the block | Yes | Yes | Yes | Yes | Yes |
| The lock of the blocked page stays held during the block | Yes | Yes | Yes | Yes | Yes |
| Largest gap of the heartbeats of the worker | 114 ms to 210 ms | 115 ms to 123 ms | 3994 ms to 4088 ms (the block) | 4070 ms to 4088 ms (the block) | Not measured (refer to the note) |
| The test closes the blocked page: the lock comes free | 0.5 s to 8 s later | 14 ms to 2.8 s later | Windows: 12 ms to 52 ms later. Linux: 3 s later | At the end of the block, also after 90 s | 3.4 s to 5.3 s later |
| `pagehide` of the closed page | No | Yes, 13 ms after the close | Windows: no. Linux: at the end of the block | Yes, at the end of the block | No |

**Note on iOS.** The earlier iOS result for the gaps of the heartbeats was not a measurement. Safari on iOS operates only the visible tab. While the test page is visible, the peer page sends no heartbeats, thus the gap was the full interval. The test checks that heartbeats arrived before and after the block, and it skips itself on iOS. The lock and the close results of the iOS column are real checks.

**Meaning.** In each engine, another page of the origin operates during the block, and the Web Lock of the blocked page stays held. Thus the other page sees the silence of the hung page, and it knows that the page still exists. The BroadcastChannel of a worker waits for the main thread in WebKit and Safari, as the other output of a worker (E6). Thus the hung page itself cannot send a message.

The engines end a page that the user closes during a hang in three ways:

- Chromium, Safari on iOS and the WebKit build for Windows stop the page. The lock comes free without `pagehide`. Then another page can report the hang.
- Firefox stops the blocked script, and Safari on macOS lets the script continue until it ends. Then the page closes normally, with `pagehide`. Thus the page itself can report its hang at its close.
- The WebKit build for Linux releases the lock after 3 s, but the page continues until the end of its script.

**Change in the library.** The [peer hang watch](/docs/monitors/peer-hang-watch) uses both paths. A visible page holds a Web Lock and sends a heartbeat each second. Another page reports a page whose lock comes free after 5 s or more without a heartbeat (`lag.hang.source: "peer"`). A page that closes at the end of a hang reports its own hang (`lag.hang.source: "self"`).

**Check in the repository.** `peer-tab.test.ts` keeps the measurements of each engine. It expects the silence, the held lock, the BroadcastChannel of a worker, and the way in which each engine ends a closed page. [`peer-hang-watch.test.ts`](https://github.com/mark1russell7/lag/blob/main/packages/lag-integration-tests/src/peer-hang-watch.test.ts) operates the library in two pages, and expects the report of the right page in each engine. It skips itself in Safari on iOS, because Safari there operates only the visible tab.

## E8: the cost of an async context in the browser

**Question.** A context manager of OpenTelemetry keeps the active span through asynchronous code. In the browser, zone.js and async-browser-context do this work on the main thread. They wrap each promise reaction, each timer and each event listener.

How much main-thread time does each one cost? Does it change the values that the monitors of lag measure, or only the cost? Which asynchronous code keeps the span?

The answer is necessary for two decisions: the default context manager of otel-ts, and an add-on of lag that uses async-browser-context. In Firefox and Safari, no Long Animation Frames entry names the script of a long task. An async context could name the operation that caused the lag.

**Method.** The package [`@lag/experiments`](https://github.com/mark1russell7/lag/tree/main/packages/experiments) builds one page with Vite in four setups. Only the setup module and the options of the build are different:

- **A. No async context.** The option of otel-ts is `contextManager: "stack"`. The `StackContextManager` patches nothing. The build replaces `@opentelemetry/context-zone` with a module without zone.js.
- **B. Zone.js.** The option of otel-ts is `contextManager: "zone"`, the default of otel-ts at this time. The zone.js library patches `Promise`, the timers and the event listeners.
- **C. AsyncBrowserContext.** The page uses the npm package `async-browser-context` 0.2.0. Its Vite plugin transforms all modules, also the dependencies. The page gives `AsyncContextManager` of `async-browser-context/opentelemetry` to otel-ts. The build also replaces `@opentelemetry/context-zone`, because the library must not operate together with zone.js.
- **D. `stack`, zone.js loaded.** The option of otel-ts is `contextManager: "stack"`, with otel-ts as the package is. The package imports `@opentelemetry/context-zone` for each value of the option, and that module loads zone.js. Thus zone.js patches the page also in this setup.

The plugin of setup C adds an import of `async-browser-context/runtime` to each module that it transforms. With pnpm, the folders of lag and otel-ts cannot resolve that import. Thus the build of setup C sets the Vite option `resolve.dedupe: ["async-browser-context"]`.

The page starts otel-ts with tracing, which registers the context manager. The instrumentations, the metrics, the logs and Faro of otel-ts are off. The spans of the page do not record, thus nothing goes to an exporter. The runner counted 0 requests to the OTLP path of the page. The monitors of `setupAllMonitors`, with the worker of lag, record into a meter in memory.

The runner opens a new browser for each page run. A page run has these phases:

1. The setup alone, idle for 10 s.
2. The setup with the monitors: 6 s to settle, then 10 s idle. Chromium gives the main-thread time of the renderer through CDP (`Performance.getMetrics`), as in the overhead benchmark.
3. MacrotaskLag and SchedulingFairnessMonitor with an interval of 200 ms, for 10 s. The monitors of the setup sample each 5 s, thus these probes give more samples.
4. Five scripted clicks with a click handler of 100 ms. Then five `setTimeout(0)` tasks of 150 ms.
5. The workloads, with the monitors stopped: one run to warm up, then five measured runs.
6. The context check.

The workloads are fixed amounts of asynchronous work:

- `promise-chain`: a chain of 50,000 `then` calls (`promiseChain` of `@lag/load`).
- `await-loop`: one async function with 50,000 `await` expressions.
- `async-calls`: 5,000 async functions at the same time, with 10 `await` expressions each.
- `microtasks`: 50,000 `queueMicrotask` callbacks, one after the other (`microtaskFlood` of `@lag/load`).
- `timers`: 2,000 `setTimeout(0)` timers at the same time.
- `events`: 50,000 calls of `dispatchEvent`, with one listener.
- `fetch`: 100 fetches of a small JSON file from the local server, 10 at the same time.
- `operations`: 200 operations at the same time, as in an application. Each one does a fetch, reads the JSON body, waits for a `setTimeout(0)`, dispatches 10 events and does 10 `await` expressions.

A round does one page run of each setup. Each round has a different order: `A B C D`, `B C D A`, `C D A B`, `D A B C` and `D C B A`. The load of the machine can change during a measurement, thus a fixed order can make one setup look slower ([performance of async-browser-context](https://github.com/mark1russell7/AsyncBrowserContext/blob/main/docs/performance.md)). A table cell gives the median of 5 rounds and, in parentheses, the lowest and the highest round. A factor compares a setup with setup A of the same round.

**Results: the `await` step in Firefox, version 0.2.0.** In Firefox, the workload `await-loop` of setup C took 84 times the time of setup A, from 79 to 140 times in the 5 rounds. The plugin changes each `await` into a step of a generator, and the runtime starts the next step with a native `then`. A native `await` needs no `then` in JavaScript. Firefox makes the promise reaction of such a step slow.

The generator without the library was slow in the same way. It took 47 times the time of a native `await`, and the transformed `await` took 69 times. Thus the cause is a slow path of the engine for such a step. Version 0.2.2 does not use that path ([version 0.2.2](#e8-version-022)).

Under Playwright, Firefox also records an async stack for each promise reaction. Without async stacks, a transformed `await` took 17 times the time of a native `await`, and 24 times with a hook. With async stacks, it took 69 to 86 times.

The setting `javascript.options.asyncstack_capture_debuggee_only: true` records async stacks only while a debugger observes the page. With that setting, the cost stayed the same, probably because Playwright controls the page as a debugger. The probe did not examine Firefox without automation. A page with open developer tools probably has the same cost.

For the microtasks of zone.js in Firefox, the probe gave 3.5 times the time, with and without async stacks. The full measurement gave 14 times, with a load of approximately 95%. Thus the direction is certain, but the size is not.

| `queueMicrotask` chain, zone.js | ×0.8 | ×10.8 | ×4.1 | ×6.8 |

The results:

- **The fix.** In Firefox, a transformed `await` of a value took 0.58 µs, and 13.8 µs with version 0.2.0. Thus the factor went from 69 to 1.8. In Chromium and WebKit, the factor stayed near 2.
- **The cost that remains in Firefox.** The runtime patches `Promise.prototype.then`, and that patch turns off the fast path of Firefox for an `await` of a promise. In the probe, each `await` of a resolved promise took approximately 2 µs more (0.48 µs and 2.70 µs). The cost is the same in code that the plugin does not transform, because the patch is global. An `await` of a value is not affected. Chromium and WebKit had no such cost.
- **The size of that cost.** The probe operated on a machine with a load of 100%. The benchmark of the library gives approximately 0.8 µs for each `await` of a promise in Firefox.
- **zone.js.** With zone.js, the global `Promise` is the promise of zone.js, thus each `await` of a promise starts a `then` of zone.js. In Firefox, such an `await` took 15 µs without async stacks, and 111 µs with them. It took 1.9 µs in Chromium and 2.5 µs in WebKit. Thus zone.js has the same type of cost in each engine, and more of it.
- **The microtasks of zone.js.** In Firefox, the chain took 10.8 times the time in this probe, and 3.5 times in the probe with version 0.2.0. Thus the factor depends on the load.

### E8: the conclusions

These results do not depend on time, thus the load does not change them:

- **What each setup keeps.** Only setup C kept the span in all cases, in the three engines. Setup B lost it after each native `await`. A native `await` does not use code that zone.js can patch. Setups A and D kept the span only in synchronous code.
- **Setup D.** The option `"stack"` loads zone.js, because otel-ts imports it for each option. Thus a user of `"stack"` pays for zone.js and gets no context.
- **The bundle size.** The zone.js library adds 12.9 KiB of gzip, and async-browser-context 0.2.0 adds 5.7 KiB.
- **The attribution.** Both libraries replace the function that the browser starts. Thus a Long Animation Frames entry names the wrapper, or no function, in place of the function of the page.

These factors were on the same side of 1 in each round:

- **The `await` step in Firefox, version 0.2.0.** The transformed `await` took 84 times the time of a native `await` (79 to 140). The probe found the cause: Firefox makes the `then` of each step slow, and async stacks make it slower. Version 0.2.2 removes most of this cost: in the probe, the factor is 1.8.
- **Promise chains with zone.js.** In setups B and D, the promise chain took 6 to 9 times the time in Chromium. It took 2.6 times the time in Firefox, and 5 to 11 times in WebKit. For comparison, the factors of setup C were 0.41 in Chromium, 1.02 in Firefox and 1.63 in WebKit.
- **Microtasks with zone.js in Firefox.** In setups B and D, they took 14 times the time (6 to 19). The probe gave 3.5 times. In Chromium, zone.js made them faster (0.57 times), because it starts many of them in one native microtask.
- **Async functions.** In Chromium, `async-calls` took 1.8 to 2.0 times the time in setups B and C. In setup C, `await-loop` took 1.3 times the time. The probe gave 1.8 times for one transformed `await` step in Chromium.
- **The task latencies of WebKit with zone.js.** In setups B and D, MacrotaskLag and SchedulingFairnessMonitor gave 1 ms to 4 ms more than in setup A of the same round.

The other results are not conclusions. The idle cost of this measurement followed the load. Thus the quiet measurement of 2026-10-11 is the estimate. It gave +5.4 ms each second for zone.js and +1.6 ms for async-browser-context 0.1.1, with 30.5 ms for the monitors alone. The workloads `events`, `fetch` and `operations` had ranges on the two sides of 1 in most engines and setups. Setup C did not change a value of the monitors in a way that the load cannot explain.

One result was not expected. In Chromium, the promise chain was faster in setup C than in setup A in 4 of 5 rounds (0.41 times the time). The experiment did not find the cause.

**Recommendation.** The owner decided two changes. otel-ts will use the runtime of async-browser-context as its default context manager, and zone.js becomes an option. An application adds the plugin of the library when it needs the span after `await`. E8 gives this data for the decision:

- **The runtime in place of zone.js.** The data supports it. The runtime kept the span in each case where zone.js kept it, and it costs less:
  - Idle page: +1.6 ms each second, against +5.4 ms for zone.js (the quiet measurement).
  - Promise chains: up to 1.6 times the time, against 2.6 to 11 times.
  - Bundle: 5.7 KiB, against 12.9 KiB.

  E8 measured the runtime together with the plugin. The cases without `await` use only the patches of the runtime. The runtime has one cost on native code. In Firefox, each `await` of a promise takes approximately 0.8 µs to 2.2 µs more (version 0.2.2). With zone.js, such an `await` takes 15 µs or more in Firefox.
- **zone.js as an option.** The data supports it, because zone.js does not keep the span after a native `await`. Setup D shows that each user of otel-ts pays for it at this time. For the option, otel-ts must load zone.js only for `"zone"`. In the version that E8 measured, the static import of `@opentelemetry/context-zone` loads it for each option. Since version 0.1.0 (commit `a291331`), otel-ts loads zone.js only through the entry `@mark1russell7/otel-ts/zone`, and its main entry uses async-browser-context.
- **The cost of the plugin for `await`.** Use version 0.2.2 or later. With version 0.2.2, a transformed `await` of a value costs approximately 2 times a native `await` in Chromium, Firefox and WebKit (0.13 µs, 0.58 µs and 0.18 µs in the probe). With version 0.2.0, it cost 69 to 84 times in Firefox.
- **The cost of the patch of `then` in Firefox.** In Firefox, each `await` of a promise costs approximately 0.8 µs to 2.2 µs more, in transformed code and in other code. Chromium and WebKit have no such cost. The patch of `Promise.prototype.then` causes it. The runtime installs that patch for all code, thus each page that loads the runtime pays it. The zone.js library has more of the same type of cost, with 15 µs to 111 µs for each `await` of one of its promises in Firefox.
- **A page without the cost.** A page that must not pay the cost of the patch loads no context library. The entry `@mark1russell7/otel-ts/core` of otel-ts 0.1.0 loads none. Then the span stays only in synchronous code, as in setup A.
- **The use of the plugin.** The plugin is necessary only for the code that needs the span after `await`. With version 0.2.2, its own cost is small, thus an application can also transform its hot loops. The options `include` and `exclude` of the plugin only select the code that the plugin transforms. That code keeps the span after `await`, and it pays the cost of a transformed step. The options do not remove the cost of the patch of `then`, because that patch is global.
- **The documentation of otel-ts.** It must give the cost of an `await` of a promise in Firefox, for the runtime and for zone.js.
- **The attribution of lag.** With the runtime as the default of otel-ts, the Long Animation Frames entries of each page with otel-ts name `asyncBrowserContextWrapper` in Chromium. Thus lag loses the name and the source position of the script that caused a long frame.
- **The add-on of lag.** Version 0.2.0 makes it possible. `addCallbackHook` starts the hook before and after each callback. The hook gets the real function, the API that started it (for example `setTimeout`, `Promise.then` or `await`) and the context of the callback. Thus the add-on can give the attribution back in Chromium. It can also give a first attribution in Firefox and Safari.
- **The cost of the hook.** The hook operates for each callback. With version 0.2.2, a hook that did nothing made each transformed `await` step 1.1 to 2 times longer, or 0.1 µs to 0.3 µs. Thus the hook of the add-on must do little work. For example, it reads the clock at the start and at the end, and it records only a long callback. E8 did not measure the idle cost of the monitors with a hook.
- **The readings of the monitors.** Setup C did not change a value that lag measures, in a way that the load cannot explain. The zone.js library made the task latencies of WebKit 1 ms to 4 ms longer. Thus the new default needs no change to the monitors.

**Run E8 again.** From the root of the repository:

```sh
pnpm experiment:e8
```

The command builds the workspace and the four pages, and it measures 5 rounds in Chromium, Firefox and WebKit. A full measurement takes approximately 65 minutes. It writes `local-experiments.e8.json` beside this page and prints the tables of this section. The options are `--engines=chromium,firefox,webkit`, `--rounds=5`, `--setups=A,B,C,D` and `--quick`. The option `--quick` only examines the harness.

The package `@lag/experiments` pins otel-ts at commit `92cd393`, the version that E8 measured. From version 0.1.0, otel-ts has the entries `/zone` and `/core`, and its main entry does not accept `"zone"`. A measurement of otel-ts 0.1.0 needs other setups.

After a stop, `--resume=<file>` takes the results of a results file or of `packages/experiments/dist/e8/partial.json`. Then the runner measures only the missing page runs. The command `pnpm --filter @lag/experiments e8:tables` prints the tables from the file. The command `pnpm --filter @lag/experiments e8:await-probe` does the probe of the `await` step, in a few minutes. Close the other programs before a measurement: the load of this measurement made the idle cost useless.

**Limits.**

- One machine with Windows 11, on AC power, with a high load from other programs (refer to the method). Only the results that do not depend on time, and the factors with all rounds on the same side of 1, are conclusions.
- Safari on macOS was not available on the machine, and the WebKit build for Windows is not Safari.
- Under Playwright, Firefox recorded async stacks, also with the setting for a debuggee only. The probe did not examine Firefox without automation. Thus the cost of an `await` step for the users of Firefox is probably the value without async stacks. The experiment did not measure it.
- The best idle cost comes from the quiet measurement of 2026-10-11, with version 0.1.1 and only Chromium.
- The full measurement used version 0.2.0. Thus the workload factors of setup C are those of version 0.2.0. Version 0.2.2 has only the probe, which operated with a load of 100% on the machine. Its times are high, and its factors are approximate.
- The workloads do only asynchronous work, thus their factors are the largest possible factors. In an application, the network, the rendering and the other work take more time.
- The page turned off the instrumentations of otel-ts. They have their own cost, which this experiment did not measure. With zone.js, the user-interaction instrumentation also uses zones.
- The runner measured builds without minification, so that the Long Animation Frames entries show the function names. The bundle sizes come from minified builds.
- Event Timing rounds a duration to 8 ms, thus a smaller difference of INP is not visible. In Chromium without cross-origin isolation, `performance.now()` has a resolution of 0.1 ms. In WebKit, it has a resolution of 1 ms.

## E9: a cross-origin frame off the screen

**Question.** A document in a frame (an iframe) can be off the screen while its `visibilityState` stays `visible`. Thus the lifecycle of the page does not pause its monitors. What do the animation frames, the idle callbacks and the timers of such a frame do? Does an `IntersectionObserver` in the frame see the change, also while the browser does not render the frame?

**Method.** The runner is [`e9-offscreen-frame/runner/run.ts`](https://github.com/mark1russell7/lag/blob/main/packages/experiments/src/e9-offscreen-frame/runner/run.ts) (`pnpm --filter @lag/experiments e9`).

A top-level page on `127.0.0.1` has a frame of 300 × 300 px from `localhost`, which is a different origin. The frame records each animation frame, each idle callback and a timer of 100 ms. An `IntersectionObserver` on its `documentElement` records each notification. The runner scrolls the frame off the screen for 4 s, and then back. The headless builds of Playwright operated on Windows 11, in three runs for each engine (2026-10-16).

| Measurement | Chromium 145 | Firefox 146 | WebKit (Playwright build 26.0) |
|---|---|---|---|
| Animation frames off the screen | None: one gap of 4000 ms to 4020 ms | One each 999 ms to 1017 ms | None: one gap of 4021 ms to 4036 ms |
| Notification "not intersecting" | 1 ms after the last frame | 16 ms to 17 ms after the last frame, before the next frame | 4 ms to 20 ms after the last frame |
| Notification "intersecting" | At the change back | At the change back | At the change back |
| Idle callbacks off the screen | No gap of more than 200 ms | No gap of more than 200 ms | No `requestIdleCallback` |
| Timer of 100 ms off the screen | No gap of more than 250 ms | No gap of more than 250 ms | Gaps of 956 ms to 1074 ms |

**Meaning.** A frame-timing monitor in such a frame records one long gap in Chromium and WebKit, and many gaps of 1 s in Firefox. The gaps are not lag. The `IntersectionObserver` gives the change in each engine, early enough to pause the monitor before the gap. The idle callbacks continue, thus the idle monitor needs no pause. In the WebKit build, the timers of the frame also slow down to approximately 1 s.

**Change in the library.** The [frame-timing monitor](/docs/monitors/frame-timing) pauses while its frame is off the screen, through `pauseWhileHidden(monitor, { offscreen: true })` and the `frameViewport` of `createBrowserDeps()`. The [timer-throttle detector](/docs/monitors/timer-throttle) counts the slow timers of the WebKit build as throttling. The other timer monitors do not pause for it.

**Check in the repository.** The unit tests of `measurement-conditions.ts`, `frame-viewport.ts`, `instrumented/frame-timing.ts` and `browser/browser-deps.ts` check the pause with a fake observer. No browser test puts a frame off the screen at this time. Thus the runner is the check of the behavior of the engines.

## Limits of the experiments

- The local experiments used one machine with Windows 11. The Safari columns of E4, E6 and E7 come from GitHub macOS runners. The iOS column of E7 comes from the iOS Simulator of such a runner. A simulator operates on the CPU of the Mac, thus its timers and its power behavior are not those of a phone.
- The engines were the headless builds of Playwright, except Safari. The WebKit build for Windows is not Safari on macOS.
- The experiments did not test Safari in Low Power Mode, or Chromium on battery power. A GitHub macOS runner refuses Low Power Mode: `sudo pmset -a lowpowermode 1` gives "LowPowerMode not supported on AC Power". Thus the unit test `DriftLag.power.test.ts` uses the timer rule of the WebKit source instead ([DriftLag](/docs/monitors/drift-lag)). On battery, Chromium uses a timer tick of 8 ms on Windows ([Bruce Dawson](https://randomascii.wordpress.com/2020/10/04/windows-timer-resolution-the-great-rule-change/)).
- E3 used approximately 30 idle windows for each engine.
- E4 used a block of 2 s. The fetch probes send their requests to the test server of Vitest on the same machine, not to a remote collector.
- E5 used one load of 4 s for each case before the change, on Windows 11. The results of the change come from three local runs, with the four browsers at the same time on the same machine. They also come from one CI run on Linux and macOS.
- E6 and E7 used blocks of 2 s to 90 s. A real hang can be longer. E7 closed the page through Playwright or WebDriver, not through the user interface of the browser.
- E9 used one cross-origin frame and the headless builds of Playwright, not Safari or Chrome. It did not test a same-origin frame, a frame with `display: none`, or a frame that the user interacted with.
- The WebKit build for Windows makes a message wait on an idle thread (E5). In the source of WebKit, the event loop schedules each task with a timer of 0 ms (`WindowEventLoop::scheduleToRun`). On Windows, that timer can wait for the system timer tick (`MainThreadSharedTimerWin.cpp`). A newer WebKit build (Playwright 1.64) needs `libGLESv2.dll` from the system, and it did not start on the test machine. Thus nobody tested a newer build.
- The browser tests of the repository operate in Chromium, Firefox, WebKit and Chrome ([testing strategy](/docs/testing/strategy)). Thus they check the two cases of E1, the two properties of E3 and the behavior of E4, E6 and E7 in the four browsers. A CI job also operates them in Safari on macOS, and another in Safari in the iOS Simulator. `browser-facts.test.ts` checks the `window` case of E1.
